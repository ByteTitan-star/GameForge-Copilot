这页讲什么

专门拆 _build_graph(ctx)：它如何把 主图 8 节点拼起来， 以及主图里的 code_qa_loop 节点如何再嵌套 CodeQaLoop 子图（code ↔ playtest ↔ diagnose）。 用浏览器打开本 HTML 即可；对照源码： backend/app/forge/graph.py、 subgraphs/code_qa_loop.py。

一句话心智模型

主图管产品流水线：策划 →（HITL）→ 美术 →（HITL）→ CodeQaLoop → promote → done。
子图只管「写出可试玩候选并冒烟通过」，最多有限次 attempt； 通过交给主图 promote，耗尽交给主图 _pause_hitl(qa_failed|sandbox_failed)。

flowchart LR U[用户需求] --> M[主图 _build_graph] M --> P[plan / art] P --> H1[HITL 确认] H1 --> S[code_qa_loop 节点] S --> L[子图 CodeQaLoop] L -->|qa_ok| D[done / promote] L -->|exhausted| H2[HITL qa_failed]

主图拓扑（_build_graph 装的就是这个）

对应 g = StateGraph(ForgeState) + add_node + add_conditional_edges + compile()。

flowchart TD START([START]) --> RS{route_start} RS -->|首次/大改| plan RS -->|改策划| revise_plan RS -->|小改有版本| code_qa_loop RS -->|纯问答| chat_reply RS -->|resume plan_confirm 同意| art_options RS -->|resume plan_confirm 修改| revise_plan RS -->|resume art_confirm 同意| art_detail RS -->|resume art_confirm 修改| revise_art_options RS -->|resume qa_failed| code_qa_loop plan --> EP([END 等人 HITL]) revise_plan --> EP chat_reply --> END1([END DONE]) art_options -->|未 pause| code_qa_loop art_options -->|paused| EA([END HITL]) revise_art_options -->|未 pause| code_qa_loop revise_art_options -->|paused| EA art_detail -->|未 pause| code_qa_loop art_detail -->|paused| EA code_qa_loop -->|qa_ok| done code_qa_loop -->|否| EQ([END 通常已 HITL]) done --> END2([END])

注意：plan / revise_plan 的边永远进 END——因为节点内部已经 _pause_hitl(plan_confirm)， 图这次 invoke 结束，等人点了再 resume 进下一截。

主图 8 个节点分别干什么

节点干什么典型暂停
chat_reply 已有版本时纯问答，不跑生成全流程 直接 DONE
plan 生成策划稿 design_doc HITL plan_confirm
revise_plan 按用户修改意见改策划 HITL plan_confirm
art_options 生成多套美术方向 HITL art_confirm
revise_art_options 按意见改美术选项 HITL art_confirm
art_detail 选定方向后写详细美术稿 / 素材 成功则进 CodeQaLoop；失败可 pause
code_qa_loop 包装并 ainvoke 子图；成功则 promote 耗尽 → qa_failed / sandbox_failed HITL
done 标 DONE、写完成消息、清 checkpoint —

每个 add_node 还可挂 Timeout / RetryPolicy（_node_kwargs → reliability/policy.py）。策略 key：plan 族用 "plan"，art 族用 "art"，子图外墙用 "code_qa_loop"。

route_start：从哪开始跑

挂在 START → conditional_edges，没有单独的 entry_router 节点。

非 resume（新 invoke）

  • entry_phase=chat → chat_reply
  • entry_phase=code → code_qa_loop（小改）
  • 默认 → plan

resume（HITL / 可恢复回来）

  • plan_confirm + 同意 → art_options
  • plan_confirm + 修改 → revise_plan
  • art_confirm + 同意 → art_detail
  • qa_failed / sandbox_failed → code_qa_loop
  • recoverable_error → 按 recovery.node 回 plan/art/code

条件边 after_*（主图为什么常 END）

函数行为含义
after_plan 永远 → END 策划节点内已 HITL pause，本趟图结束
after_art paused/failed → END；否则 → code_qa_loop 美术确认完才写码
after_code_qa qa_ok → done；否则 → END 只有冒烟通过才收尾；否则通常已 HITL

主图上的 HITL「断点」

LangGraph 一次 ainvoke 跑到 pause 就结束；用户操作后 worker resume_run 再构图、从 checkpoint 续。

  1. plan 成功 → _pause_hitl(plan_confirm) → 图 END
  2. 用户同意 → resume → art_options → _pause_hitl(art_confirm) → 图 END
  3. 用户选方向 → resume → art_detail → code_qa_loop（子图）
  4. 子图通过 → done；子图耗尽 → _pause_hitl(qa_failed|sandbox_failed)

主图节点 code_qa_loop_node：如何嵌套子图

_build_graph 里的 code_qa_loop 不是把子图拓扑直接摊平到主图，而是一个包装函数：内部 build_code_qa_loop(...).ainvoke(loop_in)，跑完再根据结果 promote 或 HITL。

sequenceDiagram participant Main as 主图 code_qa_loop_node participant Sub as 子图 build_code_qa_loop participant Exec as code_qa_exec Main->>Main: 拼 loop_in design_doc/art/attempt Main->>Sub: ainvoke(loop_in) Sub->>Exec: code_or_repair / playtest / diagnose Exec-->>Sub: 更新 CodeQaLoopState Sub-->>Main: qa_ok / exhausted / paused… alt qa_ok Main->>Main: promote_candidate 幂等 Main-->>Main: 返回 qa_ok → after_code_qa → done else exhausted Main->>Main: _pause_hitl qa_failed/sandbox_failed Main-->>Main: END end 
subgraph = build_code_qa_loop(
    code_or_repair=code_or_repair_node,  # → execute_code_or_repair
    playtest=playtest_node,              # → execute_playtest
    diagnose=diagnose_node,              # → execute_diagnose
)
result = await subgraph.ainvoke(loop_in)

三个业务节点的实现在 code_qa_exec.py；子图文件只编排边，且 禁止在子图里改 run.status / 调 _fail。

CodeQaLoop 子图拓扑

文件：backend/app/forge/subgraphs/code_qa_loop.py · 状态：CodeQaLoopState

flowchart TD START([START]) --> COR[code_or_repair] COR -->|candidate_ready| PT[playtest] COR -->|输出截断 retry| COR COR -->|其它失败| DG[diagnose] COR -->|attempt 耗尽| EX[mark_exhausted] COR -->|paused/failed| SEND([END 交主图]) PT -->|qa_ok| OK[mark_ok] PT -->|infra 临时| IR[infra_replay] PT -->|infra 永久 / 次数满| EX PT -->|产品问题| DG PT -->|paused| SEND IR --> PT DG -->|默认| COR DG -->|paused| SEND OK --> END1([END qa_ok]) EX --> END2([END exhausted])

业务三节点

  • code_or_repair 生成/修复代码 → candidate
  • playtest Playwright 冒烟
  • diagnose 分析失败原因给下一轮

控制三节点

  • infra_replay：attempt+1，同 candidate 再试玩
  • mark_ok：qa_ok=True
  • mark_exhausted：exhausted=True，主图去 HITL

after_code_or_repair（写码之后往哪走）

条件（优先级从上到下）去向
paused / failed / hitl_stopEND
candidate_readyplaytest
attempt ≥ maxmark_exhausted
输出截断错误再 code_or_repair（retry）
其它（如 build 失败）diagnose

after_playtest（试玩之后往哪走）

条件去向
qa_okmark_ok
attempt 耗尽mark_exhausted
failure_kind=infra 且永久错误立刻 exhausted（别空转）
failure_kind=infra 临时infra_replay → 再 playtest
产品/实现问题diagnose → 再 code_or_repair

成功标准是 B 档：真实可交互冒烟通过，不能用静态 DOM 检查冒充 qa_ok。

成功 vs 耗尽（接回主图）

成功

  1. 子图 mark_ok → END，result.qa_ok=True
  2. 主图幂等 promote_candidate
  3. after_code_qa → done
  4. done：DONE、清 checkpoint、推完成事件

耗尽

  1. 子图 mark_exhausted → END
  2. 主图写 failure report
  3. infra → sandbox_failed HITL
    其它 → qa_failed HITL
  4. 用户可再 resume 进 code_qa_loop（常带 code_qa_reset）
口诀： previewable ≠ publishable； build_ok ≠ qa_ok； 只有 qa_ok 才进 done / 可发布。

常见误解

误解实际
主图有 8 个节点 = 一口气跑完 中间多次 HITL pause，一次 worker 任务往往只跑一截
CodeQaLoop 是主图上的三个独立节点 主图只有一个 code_qa_loop；内部再 compile 子图
QA 失败走 _pause_recoverable 预算耗尽走 _pause_hitl；recoverable 是异常/超时另一条通道
子图失败会直接把 run 标 FAILED 子图不改 run.status；由主图决定 promote 或 HITL
entry_router 是图上的一个 node 只是 START 上的 route_start 条件边
