# GameForge Agent 技术选型分析 — 提示词

> 用法：将下方「提示词正文」整段复制到对话中；把 `docs/product/requirements-and-features.md` 全文（或关键章节）作为附件/上下文一并提供。
> 目的：基于既定产品需求，产出可决策的 Agent 架构与框架选型分析，而不是直接写代码。

---

## 提示词正文

```text
你是资深 AI Agent 架构师与技术选型顾问。请基于我提供的《GameForge 产品需求与功能说明》（纯产品文档），做「如何用 Agent 赋能该产品」的技术选型分析。

【硬约束】
1. 一切结论必须从产品需求倒推，禁止为了用某个框架而硬凑架构。
2. 先讲清问题本质与约束，再谈模式与框架；遵循第一性原理：KISS / YAGNI / 可演进。
3. 输出用简体中文；结构遵循金字塔原理：先结论与推荐，再论据与对比。
4. 本轮只做选型分析与推荐，不写生产代码、不贴大段实现。
5. 若信息不足，先列出假设并继续分析；不要卡住不答。
6. 对比时给出「推荐 / 备选 / 不推荐」及明确理由，避免和稀泥。

【产品事实摘要（以附件全文为准，冲突时以附件为准）】
- 产品：浏览器游戏 AI 创作工作区；自然语言描述玩法 → 可试玩 → 可版本管理 → 可下载/发布。
- 虚拟创作小队角色：策划 Agent、美术方向 Agent、实现 Agent、自检 Agent；创作者是导演。
- 强人机协同（HITL）：至少在「策划确认」「美术方向选择」等节点必须停下等人；支持修改回流、暂停/恢复/取消。
- 链路有阶段进度与可读反馈；失败/拦截/额度不足要可解释、可恢复。
- 还有账号、配额、发布审核、发现社区、内容安全等平台能力（这些未必都要用 Agent，请区分）。

【你要回答的核心问题】

## A. Agent 如何赋能（问题拆解）
1. 哪些能力适合用 Agent/LLM 驱动？哪些应是确定性工作流/普通业务逻辑？请用表格区分。
2. 「策划 / 美术 / 实现 / 自检」各自的输入、输出、成功标准、失败模式是什么？
3. 人机协同点（HITL）应如何建模：中断、恢复、修改意见回流、取消语义。
4. 状态与产物如何在阶段间传递（设计稿、美术方向、可玩版本、自检结果），才能支持版本追溯与重跑。

## B. 协作范式选型（先于框架）
请在下列范式中比较，并给出唯一主推荐 + 是否允许混合：

| 范式 | 简要含义 |
| --- | --- |
| 单一 Agent + 工具 | 一个大脑串行调工具 |
| 固定 Workflow / Pipeline | 预定阶段顺序，阶段内可调用模型 |
| Multi-Agent 协作（角色分工） | 多角色对话/委托，路由可能动态 |
| 图编排（Graph / State Machine） | 显式节点、边、状态、条件路由 |
| Supervisor / Router + Workers | 调度者分派给专职工人 |
| 其他你认为更贴切的范式 | 请自拟并说明 |

必须回答：
1. 对本产品，主范式是什么？为什么？
2. 「Workflow」与「Multi-Agent」在本案是对立还是可组合？如何组合才不增加不必要复杂度？
3. 哪些阶段适合强流程（固定边），哪些适合弱流程（动态路由/重试环）？
4. 并行是否值得（例如美术多方案）？代价是什么？

## C. 框架与运行时选型
在范式确定后，再比较候选框架/方案（可增减，但至少覆盖下列）：

- LangGraph（含/不含上层 Agent 抽象）
- LangChain Agents / LCEL 工作流（若单独使用）
- CrewAI
- AutoGen / AG2
- Semantic Kernel / 其他主流编排
- 自研：有限状态机 / 工作流引擎 + 薄封装 LLM 调用
- 其他你认为更合适的选项

对每个候选从这些维度打分或定性（高/中/低即可）：
1. HITL（中断、恢复、人工命令）友好度
2. 显式状态、检查点、可重跑/可恢复
3. 多角色/多节点表达力 vs 心智负担
4. 可观测性（阶段事件、进度、失败归因）
5. 异步长任务、超时、取消的适配难度
6. 与「内容安全审核、配额、发布」等非 Agent 平台能力的边界清晰度
7. 团队学习成本与长期维护成本
8. 供应商锁定与可替换性

给出：
- 首选方案（可写「X 为主，Y 为辅」）
- 明确不推荐的方案及原因
- 若 12～18 个月内需求变复杂，演进路径是什么（避免推倒重来）

## D. 参考架构蓝图（概念层）
用文字或 mermaid 描述推荐架构（保持概念层，勿绑定具体类名堆砌）：
1. 控制面：谁编排阶段、谁持久化状态、谁推送进度事件
2. 执行面：各专职节点如何调用模型/工具，如何限次重试
3. 人机面：确认/修改/取消如何进入图或工作流
4. 平台面：配额、审核、发布等与 Agent 运行时的边界
5. 最小可行切片（MVP）：第一期只做哪些节点与 HITL，哪些后置

## E. 风险、反模式与验收口径
1. 列出 Top 风险（例如：无限对话烧配额、HITL 状态丢失、阶段回退语义不清、把平台业务塞进 Agent 图等）
2. 列出应避免的反模式
3. 给出「选型正确」的验收标准（产品可感知 + 工程可验证，各 3～5 条）

【输出格式（严格按此结构）】
1. 执行摘要（≤10 行）：主结论 + 首选范式 + 首选框架
2. 需求 → 技术约束映射表
3. 范式对比与推荐
4. 框架对比与推荐（含评分表）
5. 概念架构与 MVP 切片
6. 风险 / 反模式 / 验收标准
7. 待你确认的开放问题（最多 5 个，按优先级）

【语气】
像在做架构评审：直接、可拍板、有取舍；不要营销腔，不要堆砌时髦词。
```

## 可选：追问增强包（首轮答完后再贴）

若第一轮结论已出，可用下面短提示压实决策：

```text
基于你上一轮的推荐，请再做三件事（仍不写业务代码）：

1. 把「首选方案」落成一张决策表：采纳项 / 暂缓项 / 拒绝项，每项一句话理由。
2. 写一份给技术负责人的 1 页决策备忘录（ADR 风格）：Context / Decision / Consequences。
3. 假设我们最终选用你的首选框架：列出必须自建的能力清单（框架不提供或不可靠的部分），以及可以完全交给框架的能力清单。
```

## 使用建议

| 场景 | 建议 |
| --- | --- |
| 内部技术评审 | 附上完整产品需求文档，要求输出含评分表与 ADR |
| 对比多家模型意见 | 同一提示词分别问不同模型，只保留「执行摘要 + 推荐」做并排对比 |
| 已有实现想复盘 | 在提示词末尾追加：「我们当前实现是 ……，请对照需求指出契合点与偏差，再给演进建议」 |
