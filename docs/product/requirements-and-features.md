# GameForge 产品需求与功能说明

> 文档定位：兼顾对外介绍、合作沟通与团队对齐。
> 表达原则：只描述「做什么、为谁做、做到什么程度」，不涉及实现方式与技术选型。

---

## 1. 产品概述

### 1.1 一句话定位

**GameForge** 是面向浏览器游戏的 AI 辅助创作工作区：创作者用自然语言描述玩法，由一组专职 Agent 协助完成策划、美术方向、实现与自检，经人工确认后得到可立即试玩、可管理版本、可下载或发布的游戏作品。

### 1.2 要解决的问题

独立创作者与小团队做轻量游戏时，常见卡点是：

| 痛点 | 说明 |
| --- | --- |
| 想法难落地 | 有玩法灵感，但缺完整策划与可执行方案 |
| 角色不全 | 策划、美术、实现、试玩往往需要多人接力，成本高、周期长 |
| 反馈太晚 | 要等到接近完工才能「玩一把」，方向偏了才发现 |
| 交付断裂 | 做完了也不知道如何保存版本、分享试玩、对外发布 |

### 1.3 核心价值

1. **自然语言开工**：不要求创作者先写完整设计文档，从一句玩法描述即可开始。
2. **Agent 分工协作**：策划、美术、实现、自检各有专职 Agent，像一支虚拟创作小队。
3. **人机协同把关**：关键方向由人确认；Agent 负责推进与产出，人不被流程绑架。
4. **打开即玩**：结果是可在浏览器中直接试玩的游戏，验证玩法与手感。
5. **从草稿到作品**：版本可追溯，支持下载、发布、发现与互动，形成完整创作闭环。

## 2. 目标用户与使用场景

### 2.1 目标用户

| 角色 | 诉求 |
| --- | --- |
| 独立游戏创作者 / 爱好者 | 快速把点子变成可玩原型，反复改玩法 |
| 策划或产品同学 | 用可玩结果验证创意，而不是只靠文案讨论 |
| 教学 / 工作坊组织者 | 让学员在短时间内走完「想法 → 可玩」体验 |
| 内容运营 / 社区伙伴 | 发现、试玩、收藏社区作品，扩大传播 |
| 平台运营 / 管理员 | 审核发布、管理配额与用户，保障内容与秩序 |

### 2.2 典型场景

1. **周末灵感**：创作者描述「重力反转跑酷」，确认策划与美术方向后，很快得到可试玩版本，再根据手感继续改规则。
2. **原型验证**：产品同学用自然语言写清胜负条件与操作方式，生成后直接试玩，判断创意是否值得继续投入。
3. **课堂练习**：学员注册后按提示完成一次完整创作链路；试用账号可先浏览界面与样例，再决定是否正式创作。
4. **社区发布**：作者选定满意版本提交发布；通过后出现在发现页，他人可试玩、点赞与收藏。
5. **创作者主页**：作者设置公开标识与展示名，他人通过主页浏览其已发布作品。

## 3. 端到端创作链路

四个阶段、六个关键动作。每一步都有明确的输入、确认点与产出。

| 阶段 | 关键动作 | 创作者做什么 | 阶段结果 |
| --- | --- | --- | --- |
| 创意输入 | 描述想法 | 用自然语言说明玩法、角色、规则与期望体验 | 清晰的玩法描述 |
| 策划确认 | Agent 策划 | 审阅结构化策划方案；可批准、可要求修改、可取消 | 可确认的设计方向 |
| 策划确认 | 人工确认策划 | 决定是否按此方向继续 | 已确认的策划方案 |
| 游戏生成 | Agent 推进生成 | 在美术方向等节点做选择或给出修改意见；可暂停/取消 | 可管理的游戏版本 |
| 体验交付 | 浏览器试玩 | 打开游戏，验证玩法与操作 | 真实试玩反馈 |
| 体验交付 | 下载或发布 | 下载独立可玩包，或提交发布审核 | 可交付的作品 |

**链路原则：**

- Agent 负责「整理、提议、执行、自检」；创作者负责「定方向、做取舍」。
- 不满意可回到上一确认点修改，而不是只能推倒重来。
- 生成过程有阶段进度与可读反馈，创作者始终知道「现在卡在哪一步」。

---

## 4. Agent 协作分工

GameForge 把一次创作组织为一组互相协作的 Agent，而不是单一黑盒「一句话出游戏」。创作者始终是导演；Agent 是执行小队。

### 4.1 角色一览

| Agent 角色 | 帮创作者完成什么 | 典型产出 | 是否需要人工确认 |
| --- | --- | --- | --- |
| 策划 Agent | 把零散想法整理成可执行的游戏设计 | 玩法、操作、关卡/进程、胜负与目标等策划说明 | 是（批准 / 修改 / 取消） |
| 美术方向 Agent | 根据已确认策划提出视觉风格方案 | 可选的美术方向（通常多方案对比） | 是（选择其一 / 要求重出 / 回改策划） |
| 实现 Agent | 按确认后的策划与美术方向做成可运行游戏 | 可打开试玩的游戏版本 | 过程可暂停；结果以试玩为准 |
| 自检 Agent | 对生成结果做自动试玩与质量检查 | 通过 / 未通过及可理解的问题线索 | 未通过时可选择重试、改策划或取消 |

### 4.2 人机协作规则

1. **人定方向，Agent 做重活**：玩法取舍、风格选择、是否继续，由人决定。
2. **关键节点必须可打断**：至少在策划确认、美术方向选择处停下等人。
3. **修改意见可回流**：人可要求改策划、换美术方向，或基于试玩反馈继续迭代。
4. **失败可解释、可恢复**：生成失败或自检未通过时，给出可理解的原因与可选下一步，而不是静默消失。
5. **内容有底线**：涉及不当或危险内容时，流程可中断并提示调整描述后重试。

### 4.3 创作者在链路中的决策点

- 发送 / 修改玩法需求
- 批准或修订策划
- 选择美术方向，或要求按反馈重新出方案
- 暂停、恢复或取消一次生成
- 试玩后决定：继续改、下载、或提交发布

## 5. 功能需求

以下按模块描述产品能力。每条写清「能力」与「边界」，便于对外说明与对内对齐。

### 5.1 账号与访问

| 能力 | 说明 | 边界 |
| --- | --- | --- |
| 注册与登录 | 正式账号可创作、配置个人创作偏好、管理作品 | 需完成必要的身份校验流程 |
| 试用预览 | 可浏览界面与预置样例，降低首次体验门槛 | 不可发起生成、不可改创作相关配置、不可发布/收藏/点赞等写操作 |
| 个人资料 | 设置展示名与公开标识，形成创作者主页 | 试用账号资料只读 |
| 用量感知 | 展示日用量与剩余额度，避免「做到一半突然不能用」 | 额度用尽后需等待刷新或联系管理员调整 |

### 5.2 创作工作区（Forge）

| 能力 | 说明 | 边界 |
| --- | --- | --- |
| 需求对话 | 用自然语言描述玩法；支持在对话中继续补充与修改 | 以创作者明确发送的需求为准启动一轮生成 |
| 阶段时间线 | 展示策划 → 美术 → 实现 → 自检等阶段进展 | 阶段名面向创作者可读，不暴露内部实现细节 |
| 策划确认 | 展示策划稿（玩法、操作、关卡/进程等），支持批准、修改、取消 | 未确认不得进入后续生成 |
| 美术方向确认 | 展示多套视觉方向供选择；可写修改意见后重出 | 未选择方向不得进入详细实现 |
| 进度与状态 | 正在生成、等待确认、已暂停、已完成、失败等状态清晰可见 | 同一时刻以当前进行中的任务为准引导用户回到工作区 |
| 暂停与取消 | 创作者可主动暂停或取消生成 | 取消后可改需求再开新一轮 |
| 试玩预览 | 构建成功的版本自动进入可试玩区域 | 尚无成功版本时给出明确空状态引导 |

### 5.3 游戏与版本管理

| 能力 | 说明 | 边界 |
| --- | --- | --- |
| 游戏列表 | 管理草稿、审核中、已发布等状态的游戏 | 已发布/审核中的删除需遵循保护规则（避免误删公开内容） |
| 版本历史 | 每次成功生成形成可追溯版本；可预览、下载指定版本 | 版本与试玩结果绑定，避免「不知道玩的是哪一版」 |
| 设为当前版本 | 在多个版本中指定当前对外/对内使用的版本 | 仅对有权限的所有者开放 |
| 下载 | 下载独立可玩包，便于本地打开或二次分发 | 以已成功构建的版本为下载对象 |

### 5.4 发布与审核

| 能力 | 说明 | 边界 |
| --- | --- | --- |
| 提交发布 | 选定版本填写可选说明后提交审核 | 草稿完善到可玩后再提交；试用账号不可提交 |
| 撤回审核 | 作者可撤回待审申请，回到草稿继续改 | 仅适用于待审状态 |
| 审核结果 | 通过则公开发布；驳回则可见原因并可再次提交 | 公开可见范围仅限已通过作品 |
| 下架 | 作者可将已发布作品下架 | 下架后不再作为公开可发现内容 |

### 5.5 发现与社区互动

| 能力 | 说明 | 边界 |
| --- | --- | --- |
| 发现页 | 浏览社区已发布作品，一键进入试玩 | 未发布内容不对公众展示 |
| 试玩页 | 打开即玩；展示发布信息与基础互动 | 失效或未发布链接给出明确说明 |
| 点赞 / 收藏 | 正式用户可对公开作品表态与收藏 | 试用账号不可写互动 |
| 创作者主页 | 按公开标识查看作者已发布作品列表 | 仅展示已发布内容 |

### 5.6 运营与治理（管理员）

| 能力 | 说明 | 边界 |
| --- | --- | --- |
| 发布队列 | 审核待发布申请，通过或驳回 | 驳回需可回传给作者理解的原因 |
| 已发布管理 | 管理公开作品（如精选、上下架等运营动作） | 以保障社区质量与秩序为目标 |
| 用户与配额 | 查看用户状态，调整默认或个人额度 | 管理员不可误改自身关键身份约束（按产品规则） |
| 平台设置 | 配置默认额度、限流与联系方式等 | 变更需可追溯到运营意图 |
| 内容安全策略 | 对创作输入与生成过程进行安全把关 | 命中时中断并提示用户调整，而非静默放过 |

### 5.7 体验与辅助能力

| 能力 | 说明 | 边界 |
| --- | --- | --- |
| 多语言界面 | 支持中英文等界面语言切换 | 以界面文案为主；用户创作内容本身保持原样 |
| 外观主题 | 可切换或自定义工作区视觉主题 | 主题偏好可保存在本机，换设备需重新设置 |
| 空状态与引导 | 无版本、无作品、无收藏等场景有明确下一步提示 | 避免空白页无解释 |

## 6. 非目标（明确不做）

为避免误读产品边界，以下事项**不在当前产品承诺范围**：

1. **不承诺替代完整商业游戏制作管线**：重点是轻量浏览器游戏的从想到玩，而非大型主机/端游全流程。
2. **不承诺零人工的一键完美成品**：关键创意与风格决策仍需人确认；Agent 提升效率，不取消创作者判断。
3. **不承诺任意品类与任意复杂度**：以可在浏览器中短时试玩的玩法为主；超大世界观、长剧情、重度数值养成等不作为默认目标。
4. **不承诺离线本地独立创作套件**：产品形态是在线创作工作区与浏览器试玩。
5. **不承诺无审核的任意公开**：公开发布需经过审核与内容安全策略。
6. **本文不讨论具体技术实现**：选型、框架、部署方式等不属于本需求文档范围。

## 7. 成功标准（产品侧可感知）

以下标准用于判断「需求是否被满足」，尽量用创作者与运营可直接感知的结果表述。

### 7.1 创作闭环

- 新用户能在引导下完成：**描述想法 → 确认策划 → 选择美术方向 → 得到可试玩版本**。
- 任意关键确认点都可以：**批准继续 / 提出修改 / 停止**，且状态对用户可见。
- 生成结束后，用户能在同一工作区内**立刻试玩**，而无需另找工具。

### 7.2 迭代与版本

- 用户能基于试玩反馈继续改需求，并得到**新的可区分版本**。
- 用户能指出「当前玩的是哪一版」，并能对历史版本预览或下载。

### 7.3 交付与社区

- 用户能将满意版本**下载**或**提交发布**。
- 审核通过后，作品出现在发现页，他人可试玩；作者主页可汇总已发布作品。
- 正式用户可对公开作品**点赞 / 收藏**；试用用户被清晰告知只读边界。

### 7.4 信任与秩序

- 额度不足、内容拦截、生成失败、审核驳回等，均有**可读原因与建议下一步**。
- 管理员能完成发布审核与基础治理，社区公开内容保持可控。

### 7.5 对外叙事一致性

- 对外介绍可稳定概括为：
  **「用自然语言，让 Agent 小队帮忙完成策划、美术方向、实现与自检；你来确认方向，浏览器里直接试玩，再下载或发布。」**
